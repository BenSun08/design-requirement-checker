## 问题、用户与工作流程

商用车电气／软件工程师针对每个订单，为上一代平台的驱动模块（Drive Module）编写《设计开发要求》。该文档同时承担需求、功能设计以及部分架构输入的作用，供下游软件工程师使用。目前，工程师需要逐项在 Word 文档中搜索预期功能，并人工理解描述和删除线格式。

工具将流程改为：选择本地 DOCX → 检查启用的基准项 → 审查缺失、删除线与描述变化 → 查看预期／实际内容和原文上下文 → 作出工程判断。主要用户是订单核查工程师；MVP 中基准也由同一批使用者维护，不引入角色管理或协作基础设施。

## 目标与非目标

优先保证正确性、可解释性、可追溯性、本地离线运行，并提高异常审查效率。每个正向发现都必须有可查看的证据。检测到功能不等于工程验收通过。“未配置”表示在支持的检查范围内未找到，不证明车辆实际没有该功能。

本次仅更新文档，不创建生产实现或真实解析器。已有实施计划已采用选定的 Python/PySide6 方案，但执行仍需授权。MVP 不包含云上传、AI 依赖、服务器、微服务、插件系统、文档改写、Word 自动化、团队同步或自动工程验收。浏览器原型保留为历史交互参考，不是生产 UI 代码。

## 功能要求

| ID | 要求 | 未来 MVP 的验收证据 |
|---|---|---|
| F01 | 选择本地 `.docx`、显示文件名，并在可行时支持拖放 | 选择／取消保持一致状态；不支持的文件有可操作的错误提示 |
| F02 | 明确运行核查，使用启用的基准项 | 成功完成后，每个启用项对应一个结果；旧结果不能冒充当前结果 |
| F03 | 已判定结果显示 CONFIGURED、MISSING 或 STRUCK_OUT | 状态与匹配方式、分数相互独立 |
| F04 | 显示总数、已配置、未配置、已划线、待人工核查计数，并提供筛选与搜索 | 计数来自完整的启用项结果集；筛选不改变总计 |
| F05 | 高信息密度的列表／详情工作区 | 选择结果即可查看基准、证据、比较和来源上下文 |
| F06 | 维护检查项数据 | 新增／编辑／禁用／删除、分类、规范显示名称、匹配短语、描述、别名、备注，以及稳定标识 |
| F07 | 保留文档结构和格式 | 段落／表格／run 证据与来源坐标在导入后仍可追踪 |
| F08 | 确定性检查 | 相同文档、基准和规则版本产生等价结果，无需网络 |
| F09 | 解释证据 | 可查看原始文字、命中词、转换步骤及所有相关候选 |
| F10 | 区分处理失败与未发现功能 | 提取失败不能生成“成功且全部未配置”的报告；支持范围内覆盖不完整时明确显示 LIMITED |

修改检查基准会使当前结果失效。MVP 只有一套本地可编辑基准，由使用工程师维护；启用／禁用决定当前订单的适用项。多基准、订单模板和同步不在范围内。持久化适配器／格式通过小型验证后确定，数据不能嵌入生产源码。一次核查保留所用基准快照，避免后续修改改变旧结果含义。这是来源追溯，不是规则版本管理产品。

## 状态与匹配模型

- **CONFIGURED／☑ 已配置**：接受的证据中存在有效的功能描述，不意味着全部预期要求已满足。
- **MISSING／✕ 未配置**：在成功检查的支持范围内，没有发现合格证据。
- **STRUCK_OUT／已划线（删除线）**：所有合格出现位置都全文带删除线，且没有正常、部分划线或格式未知的合格出现位置。

初始确定性引擎的 MatchType 为 EXACT、NORMALIZED、ALIAS。FUZZY 和相似度属于 V0.2；MANUAL 依赖未来的人工复核功能；SEMANTIC 仅为未来选项。EXACT 对工程师明确配置的 detectionPhrase 做字面匹配；NORMALIZED 在具名、保守的规范化之后比较；ALIAS 记录具体别名及使用的规范化。报告匹配方式时优先 exact → normalized → alias，但仍保留其他证据，排序不得丢弃相互矛盾的出现位置。

不能仅因为字面命中就显示置信度百分比。文本命中不是经过校准的正确性概率。未来算法如提供分数，须记录其类型、量纲及算法；文本相似度必须标为相似度。原型有意不显示分数。

描述比较独立使用 SAME／DIFFERENT／NOT_COMPARED，不增加文档状态。原型的 CONFIGURED 项展示 `2s → 3s`。基本预期／实际比较属于 MVP；增强自动 diff 和模糊匹配属于 V0.2。规范化不能消除数值、单位、否定、时序或控制条件。

### 未决证据不增加第四个文档状态

**已确认的保守规则：**当 resolution 为 UNRESOLVED 时，CheckResult.status 可以为空；这是处理／复核条件，不是新的 CheckStatus。不能强行将歧义证据转成 MISSING。待人工核查单独计数，总数 = 已配置 + 未配置 + 已划线 + 待人工核查。该约定已获批准：UI 显示“待人工核查”，与置信度及三个文档状态分开。原型的 11 个示例均已判定：8 个已配置、2 个未配置、1 个已划线，其中 1 个已配置项存在描述差异。

## 检查项与原文上下文

CheckItem 包括稳定 id、唯一 code、规范显示 name、detectionPhrase、category、expectedDescription、aliases、enabled 和 notes。detectionPhrase 必填，由工程师明确维护；aliases 是替代匹配短语。不能从显示名称自动推导 detectionPhrase。只有 `2门控制` 这样的宽泛短语，不能独立证明更具体的延时功能存在。

别名只表示可识别的功能名称／短语，不能笼统等同所有数值和逻辑条件。code、name、detectionPhrase 必填；拒绝重复 code；重复名称和重叠别名需提示复核。允许缺少预期描述，此时 NOT_COMPARED。别名命中本身不证明描述相同。永久删除前需确认；禁用可恢复。

DocumentLocation 在特定文档快照内标识正文／表格／行／单元格／段落位置，必要时保留嵌套表格路径。UI 坐标从 1 开始，内部约定必须明确。不承诺页码。显示命中块及相邻内容，标注表格坐标，并保留 run，以显示部分删除线。不要求安装 Word 或精确跳转到某页。

## 已确认规则与剩余验证

用户已接受确认项 1–7。下表替代原 Q1–Q9 问题，只保留需要实测的技术细节。

| 情况／原问题 | 已确认行为 |
|---|---|
| 重复出现／Q1 | 保留全部合格出现位置。一致的正常描述为 CONFIGURED；正常描述之间关键参数冲突为 UNRESOLVED。按稳定文档顺序选择初始显示证据，但它没有更高权威性。 |
| 正常与删除线并存／Q1 | UNRESOLVED；最后出现的文本或正常文本都不会自动胜出。显示全部冲突证据。 |
| 部分删除线／Q2 | 命中功能或其关联要求内容部分划线时为 UNRESOLVED。保留准确范围，不能依据“任一 run 划线”判整块已删除。有效格式未知也待人工核查。 |
| 判定条件／原提议 | 三个 CheckStatus 不变。UNRESOLVED 单独表示判定条件，status 为空，单独统计／筛选。MVP 不新增自动人工验收流程。 |
| 跨段落／Q3 | MVP 不自动跨段落或单元格拼接。只在同一段落内合并 run，并保留映射。向用户解释这一范围限制。 |
| 表格与单元格内段落 | 纳入正文／表格段落，并保留单元格来源。嵌套／合并表格遍历由 S2 验证；无法可靠覆盖的结构必须明确提示范围受限。 |
| 规范化／Q4 | 保守处理空白、块内换行和明确等价的中英文标点，保留数值、单位、否定与条件。经审查的转换白名单与偏移映射由 S6 给出，不假设可任意去标点或等同单位／数值。 |
| 相似名称、重复项、别名／Q4 | 拒绝重复 code；提示重复名称／重叠短语。无法可靠证明配置功能的候选为 UNRESOLVED，不算正向发现。MVP 不采用模糊匹配。 |
| 缺少预期描述／Q5 | 允许，只检查功能出现；comparisonState=NOT_COMPARED 并明确说明。别名命中本身不等于描述相同。 |
| 超大文档／Q6 | 需要响应式进度、取消与资源上限；限制根据代表性输入实测。 |
| 支持的文档部分／Q7 | 正文段落、表格及单元格内段落。不自动跨段匹配。发现页眉页脚、文本框、修订记录等不支持内容时明确提示范围受限。修订删除与删除线不同。 |
| 匹配词／Q9 | 必填 detectionPhrase 与显示名称独立；aliases 表示替代短语。工程师配置，不自动提词。匹配只能证明明确界定的功能身份。 |
| 基准维护与适用性／Q8 | 使用工程师维护一套本地基准，以启用／禁用控制适用性。多基准、客户／订单／车型模板和同步延期。 |
| 损坏、受保护或不支持文件 | 明确失败／不支持，不能虚构全部未配置的成功报告。 |

### 汇总判定与描述比较

先收集全部合格证据，不丢弃矛盾候选。部分／未知删除线、正常与删除线并存、关键参数冲突、功能身份有歧义时，优先输出 UNRESOLVED 和原因。否则，有正常合格证据为 CONFIGURED；只有全文划线的合格证据为 STRUCK_OUT；成功检查范围内没有合格证据为 MISSING。全部证据仍可查看。

如果功能身份已确认，单处正常要求为 `3s`、预期为 `2s`，仍是 CONFIGURED + DIFFERENT。若多处正常要求关键值矛盾，例如同时有 `2s` 和 `3s`，则为 UNRESOLVED。关联要求范围与关键参数的自动识别需要 S6 夹具验证，不能声称具备任意自然语言理解能力。不支持或不确定的描述比较为 NOT_COMPARED，不能假定 SAME。

### 检查覆盖范围与 Windows 部署

核查覆盖状态为 COMPLETE 或 LIMITED，与运行生命周期、resolution 和 CheckStatus 分开。COMPLETE 表示声明的 MVP 范围内内容均已处理，不代表支持所有 Word 特性。发现排除／不支持结构时显示 LIMITED 和原因。受限运行的 MISSING 仅表示已检查范围未找到，不代表整份文件没有。如果无法安全提取，应终止为失败。

应用须在 Windows 10/11 x64 上由普通用户离线运行，不要求用户安装 Python、Qt、Office 或开发工具。使用者没有管理员／安装权限。优先验证解压运行的便携包；只有企业策略允许免提权时才考虑用户级安装程序。不能依赖 Program Files、机器级注册表修改或 UAC 提权。可变基准／设置／日志位于用户可写位置，与程序文件分开。“便携”不代表可绕过企业执行策略；执行被阻止属于 IT 依赖，不能绕过控制。

Windows 具体构建版本、Qt/Python 版本与 IT 执行限制仍待验证。首次分发、解压／安装、首次启动和文档核查必须完全离线。无论采用何种分发格式，都必须满足无管理员权限使用。

## UX 原则

优先审查异常；紧凑桌面控件；持续显示文档身份；状态同时使用文字及符号／颜色；列表与详情同时可见；选中后立即追溯来源。不能让模拟结果看起来像来自选中文件。键盘操作与中文工程文本可读性优先于装饰。

## 生产 MVP 验收与验证

1. 支持的本地 DOCX 可以离线检查，原文件字节不变。
2. 启用项产生可重现结果或符合已确认规则的明确待核查条件；范围限制可见，汇总包含待人工核查。
3. 每个正向／已划线分类都有原始证据、格式、匹配方式和可定位来源。
4. 汇总／筛选／搜索一致；选择项目可见预期／实际内容；未配置无虚构证据。
5. 基准编辑持久化并要求重新核查；无效输入有可操作提示。
6. 正常、混合 run、表格、删除线夹具与批准的真值一致，包括错误和矛盾证据。
7. 试点用户可在 Windows 10/11 x64 无管理员／安装权限条件下，用允许的非提权格式部署、启动、打开与核查。分发包携带运行时，替换／更新时保留基准。
8. 历史文档按工程师标注真值验证；试点前约定发布阈值，不能从模拟数据宣称 precision/recall。

## V0.2 与未来

V0.2 候选：增强文本 diff、带明确相似度的模糊候选、内部预览改进、人工确认和报告导出。未来仅在需求得到证明后考虑：语义／LLM 兜底、修正内容生成、DOCX 编辑、Word 集成、批注、团队同步、规则版本工作流。它们不改变当前 MVP 架构。

## 已确认的 Python 3.8 与完全离线环境

用户说明：公司电脑目前安装 **Python 3.8**，能否升级未知。这是现有环境事实，不表示已经选择应用／构建运行时版本。保留该安装及其 PATH／文件关联，不作修改。目标仍为 **Windows 10 和 Windows 11 x64**，使用者**没有管理员／安装权限**。**首次分发、解压／安装、首次启动和正常核查必须完全离线。**

计划的自包含包须携带经过验证的 Python／Qt／原生依赖，不调用电脑中的 `python`，不要求目标机执行 `pip install`、在线激活或下载。S3 必须断网、无缓存前置依赖，分别验证与现有 Python 3.8 共存且不改动它，以及未安装 Python 的干净电脑。目前没有分发包通过这些检查。

开发／构建环境是否可用仍是独立未决项：确认能否在不改变公司安装的条件下，使用获准的隔离／较新解释器及 Windows 构建机。不能认为 Python 3.8 的 `venv` 会升级解释器。如果唯一允许的构建／运行时就是 3.8，应先评估准确兼容依赖组合及维护影响，不能悄悄锁定旧包或改变技术栈。完全离线交付不代表已经确认构建机本身能否联网；需要单独记录，并在必要时准备离线构建依赖。
