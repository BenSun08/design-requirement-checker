# Module dependencies

![Module dependency graph](module-dependencies.svg)

Open the [SVG directly](module-dependencies.svg) to zoom with the browser.
This graph is generated by **Pydeps**, filtered to repository modules. An edge
`A → B` means A imports B. Standard library and third-party nodes are omitted
for readability, and package initializer nodes are suppressed. Nested imports
are also inspected by a separate Python AST inventory.

The dominant direction is UI → Application → Matching / DOCX Adapter /
Baseline Store → Domain. UI also imports domain models because it displays
snapshots. The adapter does not call the matcher: application orchestrates both.
`__main__` deliberately knows the window, application load use case, style and
baseline path because it is the composition root.

## Boundary findings that need interpretation

`ui.main_window` imports `default_path` and `UnsupportedBaselineSchemaError`
from the store. This couples presentation to a storage path/error type beyond
the ideal UI → Application-only orchestration diagram. It does **not** perform
JSON reads or atomic writes itself; it still calls `save_baseline_to`.
Treat it as an existing boundary concern for an owner-reviewed refactor, not
as a reason to change production behavior during pack generation.

`baseline_store.default_path` lazily imports `QStandardPaths`. Constitution §4
explicitly permits this existing exception; it is not evidence that other
storage functions may use Qt. `domain` and `matching` have no Qt or I/O imports
in the inspected implementation.

The automatic check below covers selected import rules, not all possible
architectural violations. Dynamic dispatch, hidden I/O and domain decisions
inside widgets require source review.
